# Спецификация расписания и оплаты

Статус: Черновик, реализация платежей заблокирована внешними решениями

Версия: 0.1

## 1. Назначение

Дать ученику безопасный путь от выбора времени консультации к оплате услуги,
не принимая и не сохраняя реквизиты карты на сайте Electro Tutor.

## 2. Текущее состояние

- страница услуг уже читает публичную переменную `PUBLIC_CALCOM_URL`;
- при наличии URL показывается внешняя ссылка на расписание;
- при отсутствии URL показывается сообщение о будущей интеграции;
- checkout, webhook и backend отсутствуют.

## 3. Предусловия для реализации

Пользователь должен подтвердить:

1. страну регистрации получателя и юридическую/налоговую модель;
2. страны клиентов и поддерживаемые валюты;
3. тип продаваемого продукта или услуги;
4. правила возврата и требования к квитанциям;
5. выбранный платёжный провайдер и его доступность для этой модели;
6. рабочий URL Cal.com либо решение использовать другой календарь.

Поддержку отдельных карточных систем и стран нельзя предполагать заранее: её
нужно повторно проверить по актуальным правилам провайдера и применимому праву
непосредственно перед реализацией.

## 4. Функциональные требования

### FR-PAY-001 Расписание

Публичная ссылка календаря задаётся через `PUBLIC_CALCOM_URL`. Секретные OAuth
токены не попадают в клиентскую сборку.

### FR-PAY-002 Checkout

Оплата должна выполняться на hosted checkout лицензированного провайдера.
Клиентский код не принимает полный номер карты, CVC или платёжные секреты.

### FR-PAY-003 Серверное подтверждение

Статус оплаты изменяется только после проверенного server-side webhook.
Обработчик проверяет подпись, допускает безопасный повтор события и не выдаёт
результат по одному только redirect пользователя.

### FR-PAY-004 Состояния интерфейса

Пользователь видит локализованные состояния: ожидание, успех, отмена и ошибка.
Повторная отправка не должна создавать незаметный двойной заказ.

### FR-PAY-005 Возврат и поддержка

До запуска должны быть опубликованы применимые правила возврата, контакты и
необходимая информация о продавце.

## 5. Требования безопасности

- минимальные scopes и отдельные test/live credentials;
- секреты только в server-side secret storage;
- проверка происхождения и подписи webhook;
- idempotency для создания заказа и обработки события;
- журналирование без платёжных реквизитов и лишних персональных данных;
- rate limiting и безопасные сообщения об ошибках.

## 6. Критерии приёмки

- AC-PAY-001: без заполненных предусловий реализация не начинается;
- AC-PAY-002: тестовая оплата проходит полный hosted checkout сценарий;
- AC-PAY-003: поддельный webhook отклоняется, повторный не дублирует заказ;
- AC-PAY-004: секреты отсутствуют в статическом bundle и Git;
- AC-PAY-005: RU/UK состояния успеха, отмены и ошибки проверены;
- AC-PAY-006: решение о production-запуске зафиксировано в
  `docs/DECISIONS.md` после актуальной юридической и провайдерской проверки.
